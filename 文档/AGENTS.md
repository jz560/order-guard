# AGENTS.md

## 1. 项目目标与范围

项目：订单异常诊断与受控处置 Agent。

第一版只处理“支付成功，但订单仍待支付”：
查询证据 → 诊断 → 生成方案 → 人工审批 → 受控执行 → 结果验证。

唯一允许的业务写动作：
重新核验支付事实，并在满足业务条件时推进订单状态。

项目使用模拟订单、支付和回调数据，不接入真实资金。

默认不引入：
- 多 Agent、RAG、模型微调。
- Redis、消息队列、Elasticsearch、Kubernetes。
- 通用工作流引擎或复杂微服务体系。
- 退款、扣款、地址修改、物流处置。

只有任务明确要求或存在已说明的实际需要时，才扩展上述范围。

## 2. 技术栈与目录约定

技术栈：
- Java 21、Spring Boot、Spring AI。
- PostgreSQL、MyBatis、Flyway。
- Spring Security、Bean Validation。
- Vue 3、TypeScript、Vite、npm。
- JUnit、Testcontainers。
- Docker Compose。

具体依赖版本以验证后的 Maven 配置和前端锁文件为准。
不得自行使用 SNAPSHOT、动态版本或 latest 镜像标签。

建议目录：

- pom.xml：Maven 聚合工程。
- mvnw、mvnw.cmd、.mvn/：Maven Wrapper。
- backend/：业务 API、Worker、诊断、审批、执行。
- simulator/：独立业务模拟服务。
- frontend/：操作工作台。
- compose.yaml：本地演示环境。
- .env.example：配置变量示例。
- docs/：需求、技术设计、接口及运行文档。
- docs/tasks/：任务定义与完成记录。
- docs/decisions/：重要架构决策。
- scripts/：集成验证、故障实验脚本。

业务应用与模拟服务通过 HTTP 通信，使用独立数据库和账号。
禁止业务应用直接查询或修改模拟服务数据库。

若已有仓库采用不同结构，先检查现有实现，避免无必要迁移。

## 3. 构建与测试命令

以下命令由 T01 建立，并在 README 中记录前置条件。
后续任务优先使用这些入口，不另外发明重复脚本。

### 3.1 后端

在仓库根目录执行：

```bash
# 编译
./mvnw -B -ntp compile

# 单元测试
./mvnw -B -ntp test

# 完整验证：单元测试、集成测试及构建检查
./mvnw -B -ntp verify

# 构建产物，跳过测试；不能作为验证通过的证据
./mvnw -B -ntp -DskipTests package

# 代码格式检查
./mvnw -B -ntp spotless:check

# 格式化
./mvnw -B -ntp spotless:apply
```

Windows PowerShell 使用：

```powershell
.\mvnw.cmd -B -ntp verify
```

约定：
- 单元测试使用 `*Test`，由 Surefire 执行。
- 集成测试使用 `*IT`，由 Failsafe 在 verify 阶段执行。
- PostgreSQL 集成测试使用 Testcontainers，需要可用的 Docker。
- 不得用 H2 替代涉及 PostgreSQL 锁、事务或索引行为的验证。
- 测试缺少 Docker 时必须报告阻塞，不能静默跳过后声称通过。
- T01 配置并锁定 Spotless 及格式化器版本。

### 3.2 前端

在 frontend 目录执行：

```bash
npm ci
npm run lint
npm run typecheck
npm run test:unit
npm run build
npm run dev
```

约定：
- 提交 package-lock.json。
- test:unit 必须单次运行并返回退出码，不使用持续监听模式。
- T01 建立所需 scripts，禁止使用恒成功的空脚本冒充检查。
- 没有测试时应如实记录，不以空测试套件证明行为正确。

### 3.3 本地环境

在仓库根目录执行：

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=200 backend simulator
docker compose down
```

约定：
- Compose 服务名使用 backend、simulator、postgres；前端服务可后续补充。
- 默认开发模式使用模型替身，无模型密钥也能启动。
- 本地健康检查入口：
  - backend：http://localhost:8080/actuator/health
  - simulator：http://localhost:8081/actuator/health
- 端口须可配置；修改默认值时同步文档。
- 禁止将 `docker compose down -v` 写入日常停止流程。
- 删除卷、清空数据库、重置非专用测试数据，需有明确授权。
- 不得输出展开后的完整 Compose 配置，以免泄露密钥。

### 3.4 验证范围

每次变更运行直接相关的检查：
- 业务逻辑修改：相关单元测试。
- SQL、迁移、锁或事务修改：真实 PostgreSQL 集成测试。
- 接口修改：接口行为、权限与错误分支测试。
- 前端修改：lint、类型检查、构建及相关交互测试。
- 任务完成或提交 PR 前：运行可执行的完整验证。

只有为解决具体风险或满足交付要求，才扩大测试范围。
禁止反复运行无关测试代替推进任务。

## 4. 代码规范

### 4.1 通用要求

- 标识符使用清晰的英文，用户提示与项目说明默认使用中文。
- 按业务能力组织代码，避免形成巨大的通用 service 包。
- 保持改动聚焦，不顺带重构无关模块。
- 优先使用已有依赖和模式，新增依赖需说明用途。
- 不为尚未出现的需求建立通用平台或多层抽象。
- 注释解释业务原因、并发边界和限制，不复述代码。
- 不提交死代码、无意义 TODO、调试输出或未使用依赖。
- 不修改用户未授权的其他工作。

### 4.2 Java 与业务接口

- 使用构造器注入。
- Controller 负责协议与输入校验，业务规则放入业务服务。
- 请求、响应和持久化对象职责分开。
- 枚举表达受限的状态与动作，不散落魔法字符串。
- DTO 可使用 record；禁止通过反射或过度泛型隐藏业务流程。
- 时间使用 Instant 或带时区类型；数据库统一保存绝对时间。
- 用户界面按 Asia/Hong_Kong 展示，明确时间含义。
- 金额使用整数最小货币单位和币种，禁止 float/double。
- 所有外部调用设置超时；重试必须明确适用条件和上限。
- 禁止吞掉异常或将所有失败统一伪装成成功响应。
- 错误响应包含稳定错误码、可理解说明和关联 ID。
- 后端返回允许操作，前端不能自行决定业务权限。

### 4.3 数据库与事务

- Flyway 管理数据库结构。
- 已应用的迁移文件不得修改，使用新增迁移修正。
- 唯一性和幂等约束必须有数据库约束兜底。
- SQL 使用参数绑定，禁止拼接不可信输入。
- 状态转换使用明确条件和版本检查。
- 数据库事务保持短小。
- 禁止在事务内等待模型、远程 HTTP 或长时间重试。
- 修改索引和锁策略时说明对应查询与并发问题。
- 不允许通过删除记录掩盖状态机错误。

### 4.4 前端

- 使用 TypeScript，避免无说明的 any。
- 明确处理加载、空态、失败、过期和无权限状态。
- 写操作提交期间防止重复点击；后端仍须保证幂等。
- SSE 仅用于通知，API 和数据库状态是权威来源。
- 页面重载、断线重连后重新获取当前状态。
- 不向用户展示堆栈、密钥、完整提示词或模型内部推理。
- 不通过隐藏按钮代替后端授权。

## 5. AI 应用约定

- Spring AI 用于模型接入和工具交互。
- 应用控制工具循环，以便逐步持久化、检查预算和恢复。
- 模型只调用明确列出的只读工具。
- 工具访问范围从服务端任务与身份上下文获取。
- 模型提供的订单号等参数不能扩大访问权限。
- 工具结果、回调文本等外部内容视为数据，不作为系统指令。
- 校验结构化输出、动作名称、参数和证据引用。
- 仅校验 JSON 格式不代表诊断正确。
- 模型不能批准方案、修改权限或直接执行修复。
- 配置轮数、工具次数、超时、输出长度和重复调用限制。
- 证据不足时允许等待或转人工，不强制生成处置方案。
- 记录模型标识、提示词版本、用量及可获取的费用估算。
- 不把估算费用描述为精确费用上限。
- 模型恢复调用可能产生额外费用，不能宣称恰好调用一次。
- 默认测试使用模型替身；真实模型评测与普通 CI 分离。
- 未明确授权付费调用时，不批量运行真实模型评测。
- 不将测试替身的结果冒充真实模型效果。

## 6. 不可绕过的执行约束

### 6.1 审批

- 有效审批绑定方案版本、固定参数和有效期。
- 审批人来自认证上下文，不能信任请求体中的身份。
- 审批后的方案不可原地修改。
- 未批准、被拒绝或过期的方案不能开始新写操作。
- 执行前重新检查当前业务事实。
- 审批有效期控制操作的开始；已发出的操作仍需确认结果。

### 6.2 幂等与结果确认

- 业务调用前持久化执行意图和 operationId。
- 同一次操作的查询、恢复和重试使用相同 operationId。
- 下游绑定 operationId 与固定参数。
- 相同 ID、不同参数必须拒绝。
- 下游将业务更新和操作结果置于同一事务。
- HTTP 超时不等于业务失败。
- 未查到操作记录不自动等于未执行。
- 结果未知时进入 UNKNOWN，先确认再决定后续处理。
- UNKNOWN 转人工后仍保留订单处置限制。
- 最终成功必须有业务结果验证。
- 不承诺网络请求恰好发送一次；保证范围基于下游幂等契约。

### 6.3 Worker 与恢复

- Worker 根据数据库状态推进任务，不依赖页面连接。
- 使用任务认领、租约及 epoch 防止旧执行者覆盖状态。
- 租约不能替代下游幂等。
- 等待审批或下次查询时释放执行线程。
- 重启后从持久化记录恢复，不创建新操作绕过原任务。
- 取消与开始执行通过原子状态转换竞争。
- 写操作已发出后，取消不能被解释为撤销业务效果。
- 查看历史与回放记录不得重新执行业务写操作。

## 7. 配置、密钥与日志

- 提交 .env.example，只包含变量名、说明和无害示例。
- .env、真实密钥文件、证书私钥加入 .gitignore。
- 模型密钥、数据库密码等从环境变量或外部密钥系统注入。
- 禁止把真实密钥放入源码、测试夹具、文档、截图和日志。
- 禁止将后端密钥放入前端 VITE_* 变量或构建产物。
- 应用数据库账号不能访问模拟服务数据库，反之亦然。
- 模型查询凭证不得具有写操作权限。
- demo、test 与真实模型模式明确区分。
- 故障注入和数据重置入口只允许在 demo/test 环境启用。
- 除必要健康信息外，不公开敏感管理端点。
- 日志使用 taskId、operationId 等关联字段。
- 不记录认证头、密码、完整凭证或未经脱敏的敏感数据。
- 发现凭证泄露时停止传播并报告；不能仅删除代码后声称已解决。

## 8. 任务执行要求

开始任务前：
1. 阅读本文件、当前任务定义及直接相关设计。
2. 检查已有实现和工作区修改。
3. 确认依赖任务已满足；未满足时明确指出。
4. 说明本次范围、预期产物和验证方式。

执行过程中：
- 默认只完成当前指定任务，除非用户授权继续多个任务。
- 可以完成当前任务必需的、小范围依赖修复。
- 不擅自改变业务范围、审批语义、状态模型或外部契约。
- 常规实现细节自行决定，不反复请求确认。
- 发现重大设计冲突时，先说明影响，再寻求必要澄清。
- 不绕过权限、失败测试或验收要求。
- 不通过关闭测试、降低断言或捕获全部异常制造通过结果。
- 真实数据库行为用数据库验证，协议模拟不能替代集成测试。
- 不回滚、覆盖或删除无关的用户修改。
- 不执行未经授权的发布、部署、推送或破坏性操作。

重要决策记录到 docs/decisions/：
- 问题和约束。
- 选择的方案。
- 放弃的替代方案及原因。
- 适用边界和验证状态。

## 9. 测试与评测约定

优先测试：
- 并发创建同订单任务。
- 审批权限、版本、过期与重复提交。
- 审批后业务状态变化。
- 相同操作重复请求及参数冲突。
- 下游成功但响应丢失。
- 下游成功、本地落库前进程退出。
- 旧 Worker 恢复与新 Worker 竞争。
- UNKNOWN 状态限制与人工接管。
- 取消和执行认领竞争。
- 非法模型输出、越权查询、预算终止。

测试应验证外部行为、状态和业务效果，不机械镜像实现。
不为简单字段访问或低风险样式修改编写无意义测试。

AI 评测要求：
- 开发集与保留集分离。
- 记录规则、单次模型调用、Agent 三组的输入范围。
- 同时报告失败案例、转人工、耗时和用量。
- 不使用保留集反复调提示词后仍称其为独立评测。
- 不将模拟数据结果描述为真实生产收益。

## 10. 任务交付要求

完成后报告：

1. 本次完成的功能与对应任务 ID。
2. 主要文件及设计变更。
3. 数据库迁移、接口或配置变化。
4. 实际执行的构建／测试命令及结果。
5. 未执行的验证及具体原因。
6. 已知限制和后续依赖。

验证状态必须区分：
- 已实现并实际验证。
- 已实现但未运行验证。
- 仅模拟验证。
- 尚未实现。

不得：
- 未运行测试却写“测试通过”。
- 把 JavaScript 协议模拟写成 Java/PostgreSQL 集成验证。
- 把内存恢复模拟写成真实 kill -9 验证。
- 把可编译写成业务正确。
- 把阶段性产物写成整个项目完成。

完成标准：
- 当前任务的验收条件有对应证据。
- 必要的迁移、接口、配置与说明已更新。
- 没有已知的密钥泄露或未经说明的验收缺口。
- 有阻塞时交付可复现说明，不伪造完成状态。

Git 提交要求：
- 仅在当前任务或既有授权要求提交时执行提交。
- 提交内容聚焦，不混入无关文件。
- 不自动推送、合并或部署，除非已获授权。
