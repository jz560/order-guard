# 订单异常诊断与受控处置 Agent

**一个面向订单运营人员的 AI 应用：查询分散的业务证据，分析订单异常原因，提出处置建议，并在人工审批后安全执行；执行中断或结果不明时，能够恢复处理并保留完整记录。**

项目采用 Java / Spring Boot 实现业务与执行机制，以“支付成功但订单仍待支付”为第一版场景，逐步扩展到履约异常。

这是用于求职展示的个人项目。订单、支付及履约系统采用自建模拟服务，不接入真实资金，不虚构生产用户或业务收益。

## 一、解决什么问题

处理订单异常时，运营人员往往需要在订单系统、支付记录和回调日志之间反复查询：

- 支付是否真的成功？
- 支付流水是否对应这笔订单，金额是否一致？
- 回调是否到达，处理是否失败？
- 订单是否已被其他任务修复？
- 当前能否安全推进订单状态？

本项目将这条处理流程串起来：**查证据 → 分析原因 → 提出处置 → 人工审批 → 执行并验证。**

系统不仅展示模型的回答，还要处理真实软件执行中的问题，例如重复提交、审批过期、状态变化、服务超时和进程重启。

## 二、第一版业务范围

第一版只支持一种异常：

> **支付成功，但订单仍显示待支付。**

围绕这个场景，构造不同情况，避免所有任务都走向“执行修复”。

| 情况                                 | 预期行为                       |
| ------------------------------------ | ------------------------------ |
| 支付成功、订单信息匹配，回调处理失败 | 提议重新核验支付并推进订单状态 |
| 支付仍在处理中，尚未超过等待窗口     | 说明当前证据，建议等待复查     |
| 支付金额或订单关联关系存在冲突       | 停止自动处置，转人工           |
| 支付查询失败、关键记录缺失           | 补充查询；仍不足时明确无法判断 |
| 订单已经修复                         | 返回无需处理，避免重复操作     |
| 审批后订单被关闭或发生其他变化       | 拒绝执行旧方案，重新诊断       |

**唯一的写操作：重新核验支付，并在满足业务条件时推进订单状态。**

暂不支持退款、扣款、地址修改、物流异常和批量自动处置。

## 三、AI 与后端分别负责什么

| AI 负责                            | 确定性代码负责                       |
| ---------------------------------- | ------------------------------------ |
| 根据当前证据选择下一步查询工具     | 工具权限、参数校验与数据访问范围     |
| 综合订单、支付和回调信息分析原因   | 金额、关联关系及状态转换合法性检查   |
| 输出带证据引用的诊断结论           | 人工审批、审批有效期与方案版本校验   |
| 从允许的动作中提出处置建议         | 幂等执行、状态持久化、恢复与结果核验 |
| 说明证据缺口，选择继续查询或转人工 | 调用次数、超时和成本预算限制         |

**模型的建议不能直接改变订单。** 即使模型判断“可以修复”，后端仍须独立核验全部执行条件。

第一版不开放任意 SQL、Shell 或任意 HTTP 请求工具。

## 四、核心功能

### 1. 基于工具调用的异常诊断

提供少量只读工具：

- 查询订单详情。
- 查询支付状态和关联流水。
- 查询回调记录及处理结果。
- 查询历史处置记录。

Agent 在限定调用次数内选择工具，输出结构化诊断：

- 异常分类与可能原因。
- 支撑结论的证据编号。
- 缺失或冲突的信息。
- 建议动作，或者等待、转人工的理由。

页面展示可核查的证据与结论，不要求展示模型内部思考过程。

### 2. 人工审批与受控执行

审批页面展示订单、诊断依据、动作参数和预计影响。

审批绑定**具体方案版本、参数与有效期**。方案发生变化后，原审批失效。

执行前再次检查订单与支付状态。如果审批期间订单已关闭、已修复或出现冲突，停止执行并记录原因。

### 3. 可恢复执行

任务状态、工具调用结果、审批记录和执行记录持久化。

进程重启后，系统根据已保存的状态恢复处理；已经完成的写操作不能直接重做。

尤其处理这种情况：

> 下游已经完成操作，但响应超时，调用方不知道是否成功。

系统将其标记为“执行结果待确认”，使用稳定的操作 ID 查询下游结果。只有确认结果并满足重试条件后，才决定继续处理。

**避免重复操作依赖下游幂等与结果查询能力，不能仅靠本地日志保证。** 自建模拟服务需要实现这两项接口。

### 4. 执行约束与审计

支持：

- 单个订单同时只能有一个活动处置任务。
- 模型调用次数、工具调用次数及任务时长限制。
- Token 用量记录和估算费用。
- 重复无效调用检测。
- 诊断、审批、执行和验证记录查看。

历史回放使用已保存的记录，**不会重新执行写操作**。取消任务也不会自动撤销已发生的业务操作。

## 五、系统组成

| 组成           | 职责                                       |
| -------------- | ------------------------------------------ |
| 操作工作台     | 提交订单、查看证据、审批方案、查看任务结果 |
| Agent 诊断模块 | 模型调用、工具选择、结构化输出及预算控制   |
| 任务执行模块   | 状态管理、审批校验、幂等执行、异常恢复     |
| 业务模拟服务   | 提供订单、支付、回调查询和受控修复接口     |
| 场景与评测模块 | 构造异常、注入故障、验证诊断和执行结果     |

建议从 **Spring Boot 模块化单体 + PostgreSQL + 独立业务模拟服务** 起步，前端使用简单的 Vue 或 React 工作台，通过 Docker Compose 部署。

模型接入层封装为独立接口，便于替换模型和回放已保存的响应。第一版不引入多 Agent、向量数据库或复杂微服务架构。

## 六、如何证明 AI 有价值

这个项目不能只证明“模型会调用接口”，还要回答：

> 与固定规则相比，引入模型究竟改善了什么？

建立三组对照：

| 方案                 | 比较目的                               |
| -------------------- | -------------------------------------- |
| 固定规则诊断         | 验证明确、稳定的异常是否用规则就能解决 |
| 一次性提供证据给模型 | 验证多步工具调用是否确有收益           |
| Agent 按需查询证据   | 评估查询选择、信息缺失处理与额外成本   |

比较诊断正确率、证据支持程度、合理转人工比例、调用成本和耗时。各组使用相同案例，并明确可访问的信息范围。

如果规则方案已能充分覆盖该场景，应如实记录结果，保留规则优先处理明确情况的设计。**不以强行使用 AI 作为项目成功标准。**

## 七、如何证明工程可靠性

建立约 40—60 个初始回归案例，包含正常情况、信息缺失、证据冲突和执行故障。这是初始评测集，不代表生产可靠性已经得到证明。

重点演示以下情况：

| 故障或边界条件           | 应展示的结果                           |
| ------------------------ | -------------------------------------- |
| 任务运行中杀掉进程       | 重启后能识别状态并继续或安全终止       |
| 下游执行成功，但返回超时 | 进入待确认状态，查询结果，避免重复执行 |
| 重复提交或重复审批       | 不重复创建有效处置或产生重复业务效果   |
| 审批过期                 | 拒绝执行，要求重新确认                 |
| 审批后订单状态变化       | 执行前拦截过时方案                     |
| 模型重复查询或超出预算   | 停止调用并留下明确原因                 |
| 证据不足或相互矛盾       | 不强行归因、不执行修复                 |

AI 诊断质量与执行机制可靠性分开评测。验证恢复机制时，可以固定模型输出，避免模型波动干扰结果。

## 八、实施顺序与完成标准

| 阶段                   | 交付内容                                                     | 完成标准                                     |
| ---------------------- | ------------------------------------------------------------ | -------------------------------------------- |
| 第一阶段：完整业务闭环 | 单一异常、只读诊断、审批、一个写动作、结果验证；同时具备基本持久化与幂等设计 | 能处理成功、无需处理、冲突、证据不足四类结果 |
| 第二阶段：故障恢复     | 进程重启、执行结果待确认、重复审批、过期与状态变化处理       | 关键故障案例可重复运行，并能解释状态变化     |
| 第三阶段：评测与展示   | 对照实验、回归集、成本记录、部署文档和演示脚本               | 他人能启动系统、复现案例、检查评测结果       |
| 后续扩展               | 增加“已付款但履约任务未创建”                                 | 复用已有执行机制，明确新增业务逻辑           |

第一版完成后就可以用于面试展示，不必等所有扩展完成。

## 九、面试中展示什么

项目最终应提供：

- 可启动的代码仓库与部署说明。
- 一条完整业务演示。
- 两到三个可复现的故障恢复演示。
- 带证据引用的诊断记录与操作审计。
- 规则、单次模型调用和 Agent 的评测对比。
- 设计取舍说明：为什么需要 AI、哪些地方不用 AI、哪些能力依赖下游支持。

这个项目最值得讲清楚的是：**你如何把模型的不确定判断，接入一个有明确业务约束、可验证执行结果、能够处理失败的软件系统。**
