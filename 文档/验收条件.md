下面按第一版范围梳理：**处理“支付成功，但订单仍待支付”，唯一允许的写操作是重新核验支付并推进订单状态。**

业务参与者包括操作员、审批员、诊断 Agent、任务执行服务，以及模拟订单／支付服务。

## 一、业务流程

### 1. 提交订单并创建任务

操作员输入订单号。系统检查访问权限、订单是否存在，以及该订单是否已有活动处置任务。

- 检查通过：创建任务，开始诊断。
- 已有活动任务：返回已有任务，不重复创建。
- 无权限或订单不存在：拒绝创建，说明原因。

### 2. 查询证据并诊断

Agent 在调用预算内查询订单、支付流水、回调记录和历史处置记录，形成带证据引用的结论。

诊断结果分为四类：

| 结果     | 典型情况                                           | 后续处理                       |
| -------- | -------------------------------------------------- | ------------------------------ |
| 无需处理 | 订单已经修复，或不存在目标异常                     | 结束任务                       |
| 等待复查 | 支付仍在处理中，尚处于合理等待窗口                 | 结束本次任务；稍后人工重新发起 |
| 转人工   | 金额冲突、关联关系异常、关键证据缺失或查询预算耗尽 | 结束自动处理，保留证据与原因   |
| 建议修复 | 支付成功且信息一致，订单待支付，有证据支持修复     | 创建方案，等待审批             |

**模型输出的“建议修复”必须通过代码校验，才能进入审批。**

### 3. 审批处置方案

审批员查看诊断依据、动作参数和预计影响，然后批准或拒绝。

审批绑定具体方案版本、参数及有效期：

- 拒绝：结束任务。
- 过期：不得执行，结束当前审批流程。
- 批准且有效：进入待执行状态。
- 重复批准：返回已有结果，不重复触发执行。

第一版中，方案变更、审批过期后通过新任务重新诊断和审批，避免复杂的任务内多版本循环。

### 4. 执行前复核

执行服务重新查询当前业务事实，不直接使用诊断时的旧数据执行。

- 订单已经修复：以“无需执行，目标已达成”结束。
- 订单关闭、金额不符、支付状态变化等：拦截操作，转人工。
- 审批已失效：停止执行。
- 全部条件满足：使用持久化的操作 ID 发起修复。

**订单服务也必须在实际更新时原子校验状态与业务约束，避免“复核通过后、写入前”发生并发变化。**

### 5. 执行、核验与结束

- 明确成功：查询订单最终状态并验证。
- 明确业务拒绝：停止自动重试，记录原因。
- 超时、断连或响应丢失：标记为“结果待确认”，查询操作结果。
- 只有确认可以安全重试时，才使用同一个操作 ID 重试。
- 超过查询或重试限制仍无法确认：转人工，保留未确认操作，阻止再次发起冲突的修复。

## 三、业务验收条件

以下条件应可通过界面、接口响应、数据库记录或自动化测试验证。

### 1. 创建与诊断

| 编号 | 场景           | 验收条件                                                     |
| ---- | -------------- | ------------------------------------------------------------ |
| AC01 | 正常创建       | 有权限的用户提交有效订单号，生成唯一任务 ID，任务及初始状态持久化 |
| AC02 | 重复提交       | 同一订单已有活动任务时，重复请求返回已有任务；并发提交也不会生成两个活动任务 |
| AC03 | 无权限访问     | 后端拒绝请求，不返回该订单的业务证据                         |
| AC04 | 正常修复案例   | 对支付成功、信息匹配且回调处理失败的预置案例，生成带有效证据引用的修复建议 |
| AC05 | 无需处理       | 订单已修复时，结论为无需处理，不创建可执行修复方案           |
| AC06 | 等待复查       | 支付处理中且未超过等待窗口时，给出等待理由，不执行修复       |
| AC07 | 冲突或证据不足 | 金额不符、关联关系冲突或关键证据缺失时，不进入修复执行流程，明确标注原因 |
| AC08 | 非法模型输出   | 不存在的证据编号、未知动作或非法参数不能成为有效方案；有限次纠正失败后停止自动处理 |
| AC09 | 调用预算       | 达到配置的调用或时长限制后，不再发起新的模型／工具调用，并保存终止原因 |

### 2. 审批与执行

| 编号 | 场景             | 验收条件                                                     |
| ---- | ---------------- | ------------------------------------------------------------ |
| AC10 | 未审批           | 即使模型建议修复，也不会调用写接口                           |
| AC11 | 审批权限         | 无审批权限的账号无法通过接口批准方案；仅隐藏前端按钮不算通过 |
| AC12 | 审批绑定         | 修改方案参数或版本后，旧审批不能授权新方案执行               |
| AC13 | 重复审批         | 多次批准同一方案最多产生一次有效执行调度，返回一致的审批结果 |
| AC14 | 拒绝或过期       | 被拒绝、过期的方案不会开始新的写操作，并记录明确原因         |
| AC15 | 审批后状态变化   | 审批后订单关闭、金额或关联关系发生冲突，执行被拦截           |
| AC16 | 并发状态变化     | 执行前复核之后订单发生变化，下游仍通过原子条件检查阻止非法状态转换 |
| AC17 | 已被其他流程修复 | 记录目标已达成，不重复产生业务效果                           |
| AC18 | 执行幂等         | 同一操作 ID 被重复或并发调用，最多产生一次业务状态变更       |
| AC19 | 成功验证         | 只有操作结果与最终业务状态符合预期时，任务才标记为修复成功；接口返回成功本身不够 |

### 3. 故障恢复与取消

| 编号 | 场景                       | 验收条件                                                     |
| ---- | -------------------------- | ------------------------------------------------------------ |
| AC20 | 下游成功但响应超时         | 系统进入结果待确认；通过原操作 ID 查询后确认成功，不产生第二次业务效果 |
| AC21 | 写请求发出前进程退出       | 重启后能根据持久化记录继续处理，始终使用原操作 ID            |
| AC22 | 下游成功后、本地落库前退出 | 重启后先确认下游结果，不直接生成新操作再次执行               |
| AC23 | 两个执行者竞争任务         | 只有有效认领者可以推进当前任务；重复调用仍由下游幂等兜底     |
| AC24 | 长时间无法确认             | 达到配置的确认期限后转人工，不标记成功或确定失败；阻止新任务绕过该未确认操作再次修复 |
| AC25 | 执行前取消                 | 取消成功后不得开始写操作；取消与执行认领并发时，结果必须明确、一致 |
| AC26 | 写请求发出后取消           | 页面明确提示无法保证撤销，系统继续确认已发出操作的结果       |
| AC27 | 历史回放                   | 查看历史记录不产生模型调用、工具调用或业务写操作             |

## 四、第一版通过验收的判定

**工程约束与 AI 效果应分开验收。**

- **工程约束：**上述审批、权限、状态转换、幂等与恢复测试必须通过。在定义的测试集内，不得出现未经审批执行、重复业务效果、冲突条件下推进订单、结果不明却标记成功。
- **AI 效果：**先用开发案例调试，再冻结提示词和配置，在单独保留的案例上评测。报告诊断正确率、证据有效性、错误处置建议、转人工情况、耗时和费用。
- **业务闭环：**至少完整演示一次成功修复、一次证据冲突转人工、一次审批后状态变化拦截，以及一次“下游成功但响应丢失”的恢复。

**第一版不要求 Agent 必须胜过规则方案，但必须能用结果说明它在哪些情况有价值、在哪些情况没有优势。** 这也是项目验收的一部分。
