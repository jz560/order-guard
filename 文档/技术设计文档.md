### 1. 范围与关键约束

第一版处理“支付成功，但订单仍待支付”，仅支持一个写动作：

> 核验支付事实，并将符合条件的订单从待支付推进到已支付。

必须始终成立的约束：

1. 没有有效审批，不允许开始写操作。
2. 审批绑定具体订单、动作、参数和方案版本。
3. 同一次处置使用固定操作 ID；重试不得换 ID。
4. 下游原子完成“业务状态更新＋操作结果记录”。
5. 结果不明不能标记失败，也不能释放订单限制后重新修复。
6. 模型输出不能绕过权限、金额及状态校验。
7. 数据库事务不跨越模型调用或远程 HTTP 调用。

模拟业务第一版不包含退款、撤销支付、多币种和部分支付。金额使用整数分，支付成功事实在当前场景中不再逆转。这些边界必须写进 README。

### 2. 架构

采用 **模块化单体＋独立业务模拟服务**。两者通过 HTTP 通信，数据库权限隔离。![架构](D:\LLM dev\Order Anomaly Diagnosis and Controlled Handling Agent\架构.png)

模块职责：

| 模块         | 职责                                         |
| ------------ | -------------------------------------------- |
| `task`       | 创建任务、状态转换、任务认领、取消、恢复     |
| `diagnosis`  | 模型调用、证据收集、工具循环、结构化结果校验 |
| `approval`   | 方案冻结、审批权限、版本和有效期检查         |
| `execution`  | 操作 ID、受控写调用、结果确认、最终验证      |
| `audit`      | 步骤记录、证据快照、操作追溯                 |
| `simulator`  | 模拟订单、支付、回调及故障                   |
| `evaluation` | 固定案例、对照方案、结果统计                 |

第一版 API 与 Worker 可以在同一应用运行，但 Worker 逻辑不得依赖某个 HTTP 请求存活。

### 4. 数据模型

业务事实和执行记录分开保存。诊断时看到的订单快照，不能当作执行时的最新状态。

**应用数据库**

| 表            | 主要字段                                                     | 约束／用途                              |
| ------------- | ------------------------------------------------------------ | --------------------------------------- |
| `task`        | `id, order_id, state, outcome, version, lease_owner, lease_until, lease_epoch, next_run_at` | 任务状态及执行认领                      |
| `order_guard` | `order_id, task_id, reason`                                  | `order_id` 主键；限制同一订单的冲突处置 |
| `task_step`   | `id, task_id, seq, type, status, input, output, started_at, finished_at` | `(task_id, seq)` 唯一；保存调用与结果   |
| `evidence`    | `id, task_id, source, business_version, payload, fetched_at` | 证据快照，只追加                        |
| `plan`        | `id, task_id, version, action, canonical_params, params_hash, expires_at` | 冻结方案，审批后不可原地修改            |
| `approval`    | `id, plan_id, decision, approver_id, decided_at`             | 每个方案最多一个最终决定                |
| `execution`   | `operation_id, plan_id, status, attempts, next_check_at, last_error` | `operation_id` 主键，`plan_id` 唯一     |
| `audit_event` | `id, task_id, actor, event_type, payload, created_at`        | 审批、取消和状态转换的业务审计          |

**模拟业务数据库**

| 表           | 主要字段                                                     | 约束／用途                     |
| ------------ | ------------------------------------------------------------ | ------------------------------ |
| `orders`     | `id, status, amount_minor, currency, payment_id, version`    | 订单状态与版本                 |
| `payments`   | `id, order_id, status, amount_minor, currency`               | 支付事实                       |
| `callbacks`  | `id, payment_id, received_at, result, error_code`            | 诊断证据                       |
| `operations` | `operation_id, request_hash, result, before_version, after_version` | 幂等记录，与订单更新同事务提交 |

`order_guard` 不能只依据“任务是否结束”释放。例如任务转人工但写操作仍不确定，限制必须保留。

### 5. 状态模型

任务状态控制流程，`outcome` 解释结果，避免把所有结果都塞进状态枚举。

![状态模型](D:\LLM dev\Order Anomaly Diagnosis and Controlled Handling Agent\状态模型.png)

取消只允许发生在写执行被授权启动之前。取消和进入 `EXECUTING` 通过数据库条件更新竞争，只有一方成功。

审批有效期按“是否允许开始该操作”判断。操作已经发出后，即使审批过期，也要继续查询结果；不得创建新操作绕过过期审批。

### 6. 关键实现方式

**任务认领**

使用短事务认领到期任务，并增加 `lease_epoch`。Worker 更新任务时必须携带自己的 epoch，旧 Worker 不能覆盖新 Worker 的结果。

PostgreSQL 的 `FOR UPDATE SKIP LOCKED` 适合多个消费者竞争队列记录；它只解决认领阶段的行锁竞争，不保证外部调用只发生一次。[postgresql.org](https://www.postgresql.org/docs/18/sql-select.html?utm_source=chatgpt.com)

外部操作仍需依靠固定操作 ID 和下游幂等兜底。

**审批与执行意图**

在一个事务中：

1. 锁定任务与方案。
2. 验证审批、有效期、方案参数及任务状态。
3. 创建唯一 `execution`，生成并持久化操作 ID。
4. 将任务切换到 `EXECUTING`。
5. 提交事务，然后发起 HTTP 请求。

进程在第 5 步之后任意位置退出，恢复时都使用原操作 ID。

**下游幂等事务**

模拟服务接到请求后：

1. 按操作 ID 检查已有结果。
2. 已存在且参数一致：返回原结果。
3. 已存在但参数不同：返回幂等冲突。
4. 新操作：锁定订单，核验支付、金额、币种、关联关系及状态。
5. 同事务提交订单更新和操作结果。

模拟服务把订单和支付事实置于自己的事务边界内。未来接入独立真实支付系统时，需要重新设计事实核验协议，不能把这里的原子性直接套过去。

**结果待确认**

查询操作结果时区分：

- 已成功：进入业务结果验证。
- 明确拒绝：记录原因。
- 处理中：延后查询。
- 未查到或不可访问：保持不确定。

第一版保守处理“未查到”：不自动判定未执行。若未来增加重发，也只能沿用原 ID、原参数，并依赖下游强幂等契约。

**Agent 循环**

每轮执行：

> 检查预算 → 调用模型 → 保存响应 → 校验工具名及参数 → 保存调用意图 → 执行只读查询 → 保存证据 → 下一轮。

订单范围由服务端任务上下文绑定，不允许模型任意查询其他订单。

诊断中断后可以使用已保存证据重新调用模型；不保证生成完全相同的答案，也不能保证重启不会重复产生模型费用。

### 7. API 设计

**工作台接口**

| 接口                            | 输入                                    | 结果／语义                            |
| ------------------------------- | --------------------------------------- | ------------------------------------- |
| `POST /api/tasks`               | `orderId`；创建请求幂等键               | 创建任务；订单被占用时返回对应任务    |
| `GET /api/tasks`                | 订单、状态、分页                        | 任务列表                              |
| `GET /api/tasks/{id}`           | 任务 ID                                 | 权威状态、结论、允许操作              |
| `GET /api/tasks/{id}/evidence`  | 任务 ID                                 | 证据快照                              |
| `GET /api/tasks/{id}/steps`     | 游标、条数                              | 调用与执行记录                        |
| `POST /api/plans/{id}/decision` | `version, paramsHash, decision, reason` | 批准或拒绝；冲突返回 409              |
| `POST /api/tasks/{id}/cancel`   | 预期任务版本                            | 成功取消，或返回已进入执行阶段        |
| `GET /api/tasks/{id}/events`    | SSE 连接                                | 状态变化通知；重连后重新 GET 当前状态 |

审批人从认证上下文获取，不能相信请求体中的用户 ID。所有审批与取消操作记录审计事件。

**模拟业务接口**

| 接口                                     | 用途             |
| ---------------------------------------- | ---------------- |
| `GET /internal/orders/{id}`              | 查询订单         |
| `GET /internal/payments/{id}`            | 查询支付         |
| `GET /internal/payments/{id}/callbacks`  | 查询回调         |
| `PUT /internal/operations/{operationId}` | 幂等提交修复操作 |
| `GET /internal/operations/{operationId}` | 查询操作结果     |

写请求包含固定的订单 ID、支付 ID、金额、币种、预期订单版本及动作类型。

模型查询工具只有读接口权限。写接口凭证只交给执行服务。

### 8. 初始运行参数

以下为可调整的开发起点，不是性能承诺：

| 参数                     | 初始值                        |
| ------------------------ | ----------------------------- |
| 模型轮数上限             | 6                             |
| 工具调用上限             | 12                            |
| 连续相同且无新信息的调用 | 2 次后停止                    |
| 单次模型超时             | 30 秒                         |
| 诊断总时限               | 120 秒                        |
| 审批有效期               | 15 分钟                       |
| 业务 HTTP 超时           | 3 秒                          |
| 结果确认间隔             | 2、5、10、30 秒，之后每 30 秒 |
| 自动确认期限             | 5 分钟，之后转人工并保留限制  |

成本控制采用“调用前预估＋输出上限＋调用后累计”。供应商费用和超时请求用量可能无法立即获知，因此不宣称精确的硬费用上限。
