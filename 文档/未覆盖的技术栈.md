**二、尚未覆盖，但可以自然应用到 P11 的技术栈**

以下是设计建议，并不是说必须全部加入。

| 技术栈                                 | 对应 JD 示例                                 | 如何应用到项目                                 | 建议                                                       |
| -------------------------------------- | -------------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| **MyBatis／JPA**                       | 睿服、方舟健客、药师帮等                     | 操作任务、审批和执行记录；实现条件更新和乐观锁 | **选一个加入**。结合 Java 岗位，可优先 MyBatis             |
| **自动化测试、CI/CD**                  | 方舟健客、侨银、锐竞等                       | 自动运行状态转换、幂等、恢复测试及构建部署     | **优先加入**，直接支撑项目可信度                           |
| **OpenTelemetry、Prometheus／Grafana** | 中电金信的 DevOps JD；其他岗位也要求可观测性 | 串联任务、模型和业务调用；观察耗时、失败与预算 | **推荐适度加入**，先完成一条可追踪链路                     |
| **SSE**                                | 侨银                                         | 向页面推送诊断进度、审批状态、执行结果         | **推荐加入**，用途明确，前端实现范围可控                   |
| **Elasticsearch**                      | 三横、方舟健客、药师帮等                     | 检索历史异常案例、回调日志、处置文档           | **第二阶段考虑**，你已有经验；数据很少时不必为了关键词引入 |
| **RAG＋向量检索**                      | 侨银、海之鑫等                               | 检索异常处理 SOP，引用适用条件、版本与处理依据 | **AI 岗位优先时考虑**，需要增加独立检索评测                |
| **Redis**                              | 多个 Java 岗位                               | 接口限流、短期缓存等                           | **按需求加入**；不能取代数据库中的任务和审批记录           |
| **RabbitMQ／Kafka 等消息队列**         | 视波、方舟健客、骏伯、药师帮等               | 接收支付异常事件，异步触发诊断任务             | **后续选一个**，需要同时处理重复消费和消息一致性           |
| **Kubernetes**                         | 锐竞第 30 条、部分部署要求                   | 部署服务、验证实例重启与多实例运行             | **定向投递再加**；普通部署仍不等于 K8s 任务平台经验        |
| **Python／FastAPI**                    | 侨银、部分 AI 岗位                           | 在确有 Python 依赖时提供独立 AI 服务           | **当前不急着加**，仅转发模型调用会造成重复架构             |

其中，RAG 应当有清楚的业务位置：

> 支付事实通过业务工具获取；处理规范通过文档检索获取；最终能否执行仍由代码校验。

如果只是放入十篇文档、检索后拼进提示词，只能展示基础接入。要证明 JD 中的 RAG 工程能力，还需要处理文档版本、切分、召回、引用正确性和检索失败。

**三、未覆盖，当前也不建议为了匹配关键词强行加入的技术栈**

| 技术栈／要求                                      | 对应 JD 示例               | 不建议当前加入的原因                                         |
| ------------------------------------------------- | -------------------------- | ------------------------------------------------------------ |
| **LangChain／LangGraph／LlamaIndex**              | 海之鑫、侨银等             | 可以作为替代或特定模块方案，但与 Spring AI 并用必须有实际理由；框架越多不代表能力越强 |
| **多 Agent、AutoGen 等**                          | 滴普、海之鑫等             | 当前单场景没有明确的多角色协作需求                           |
| **LoRA／QLoRA 微调、训练**                        | 海之鑫                     | 当前首先需要验证工具、数据和流程，尚无必须微调的依据         |
| **Ollama／vLLM 本地推理部署**                     | 侨银加分项                 | 可以扩展，但模型服务部署与当前核心目标分开，先不扩大范围     |
| **Spring Cloud、Dubbo、Nacos、复杂微服务治理**    | 方舟健客、骏伯、河南诚易等 | 个人项目规模暂时不需要完整微服务体系                         |
| **Flowable／Activiti／BPMN**                      | 三横加分项                 | 当前流程固定，数据库状态机即可；未来出现可配置审批流程才更有价值 |
| **MongoDB、OceanBase、TiDB、Doris、StarRocks 等** | 多家不同方向岗位           | 当前 PostgreSQL 已能满足需求，没有必要同时堆多个数据库       |
| **Netty、底层网络开发**                           | 睿服等                     | 普通 HTTP 接口和进度推送不需要自行实现网络层                 |
| **Electron、Rust 等**                             | 滴普、阅芯的相关要求       | 与当前 Web 工作台的核心需求联系较弱                          |

另外，**JVM 调优、SQL 优化、高并发、DDD 不是装上某个依赖就能覆盖的技术栈**。例如要证明 SQL 优化，就要有可复现的慢查询、执行计划和优化前后结果；要证明并发控制，就要演示两个执行者同时处理同一订单时的行为。

针对你“尽快形成可投递项目”的目标，我建议分成两档：

- **第一版确定采用：**Java、Spring Boot、Spring AI、PostgreSQL、MyBatis、基础 Vue 或 React、Docker Compose，加上自动化测试、基础 CI 和任务追踪。
- **第一版完成后按目标岗位补一条：**偏 AI 应用，补有评测的 RAG；偏 Java 后端，补消息驱动和并发故障验证；明确投锐竞执行平台，再补 Kubernetes。

**最值得补的是能产生实际证据的技术，而不是能让技术栈列表变长的技术。** 对 P11 而言，测试、追踪、可靠执行的优先级，高于再引入一种数据库或 Agent 框架。
