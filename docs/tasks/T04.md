# T04：验证幂等与真实进程恢复

## 范围

依赖 T01，交付最小调用方与独立 HTTP 下游，验证固定操作 ID、原子结果落库、响应丢失及真实进程退出后的恢复。实验不依赖模型，没有收费调用。正式任务、人工审批、Worker、完整业务模拟和前端处置页面留在后续任务。

- `backend/.../recovery/`：持久化意图、发送和恢复 CLI。
- `simulator/.../recovery/`：原子业务核验与 HTTP 幂等下游。
- `simulator/.../T04RecoveryIT.java`：独立真实进程与 PostgreSQL 实验。
- `scripts/t04-verify.ps1`：从根目录构建并运行 T04 验证，输出证据目录。
- [决策 004](../decisions/004-t04-idempotency-recovery.md)：协议选择和适用范围。

## 数据与状态

调用方使用 `agent_app` 的 `backend_app`；下游使用 `agent_simulator` 的 `simulator_app`。只有测试断言夹具拥有两个数据库的管理访问；应用进程不跨库访问。

实验显式执行 `db/t04-caller/V1__probe_intent.sql` 和 `db/t04-simulator/V1__probe_downstream.sql`，分别创建 `t04_probe` schema 和独立 Flyway 历史。普通 Spring Boot 的默认迁移仍只有服务归属标记 V1。没有修改已应用迁移，没有迁移或清空 T01 数据。

调用方：PREPARED → IN_FLIGHT → SUCCEEDED / REJECTED / UNKNOWN。先提交操作 ID 和固定参数，原子认领后才 HTTP 写入。UNKNOWN 沿用原 ID 查询，不创建新操作，不解除订单限制；本实验的唯一订单约束始终保留。

下游：操作 ID 主键、完整参数和规范哈希共同绑定请求；订单行锁与版本条件更新防止竞争推进。业务状态更新与操作终态同事务提交，结果保存失败时二者一起回滚。

## 接口与配置

只在独立实验进程中提供以下接口，默认普通服务仍只开放健康检查。

| 接口 | 凭证 | 行为 |
| --- | --- | --- |
| `PUT /t04/operations/{UUID}` | 写凭证 | 核验并推进，或返回原结果；参数冲突 409 |
| `GET /t04/operations/{UUID}` | 读凭证 | 成功 200、业务拒绝 422、未找到 404 |
| `GET /t04/orders/{id}` | 读凭证 | 查询当前业务事实，供调用方最终验证 |
| `GET /t04/stats` | 读凭证 | 当前下游进程收到的写请求和查询次数，仅实验观测 |
| `GET /health` | 无 | 最小进程存活信息 |

请求字段：orderId、paymentId、amountMinor、currency、expectedVersion、action。唯一动作 `VERIFY_PAYMENT_AND_ADVANCE_ORDER`。拒绝非法字段、重复 JSON 键、尾随内容、无效金额和币种。只读凭证不可写，读写 token 必须不同且至少 16 字符。

主要返回码：`OPERATION_ID_CONFLICT` 表示 ID 已绑定其他参数；`BUSINESS_PRECONDITION_FAILED` 表示当前业务条件不满足；`OPERATION_NOT_FOUND` 仅表示此次查询未找到。接口错误带稳定 code、中文 message 与 correlationId，不输出数据库堆栈或凭证。422 为已落库的业务拒绝结果，与普通接口错误结构不同。

CLI 共同环境变量：`T04_MODE=demo/test`、`T04_DB_URL`、`T04_DB_USER`、`T04_DB_PASSWORD`。调用方另需 `T04_OPERATION_ID`，命令 `prepare/send/recover`；send/prepare 使用 `T04_ORDER_ID`，send/recover 使用 `T04_DOWNSTREAM_URL`、`T04_READ_TOKEN`，仅 send 需要 `T04_WRITE_TOKEN`。

下游使用 `T04_READ_TOKEN`、`T04_WRITE_TOKEN`，默认端口 `T04_PORT=8094`，可通过 `T04_SEED_ORDER_ID` 插入一个新实验订单（不会覆盖已有订单）。`T04_FAULT=DROP_RESPONSE` 在事务提交后截断响应；`T04_PAUSE=AFTER_RESPONSE_BEFORE_SAVE` 使调用方在收到响应、本地写入前停住，由测试发送 SIGKILL。故障设置仅显式 demo/test 实验入口接受。

HTTP 连接及请求各设置 3 秒超时，不自动重试。调用方输出 `T04_RESULT`；退出码 0 只表示命令正常结束，必须查看 status，不能将 UNKNOWN 当作成功。无效输入或存储启动异常退出 2。恢复仅 GET，下游报成功仍需验证订单状态、关联支付、金额、币种和版本；核验失败保持 UNKNOWN。

## 已知限制

这是执行协议的阶段验收，不是正式订单处置功能。没有审批界面、生产鉴权、恢复 Worker、租约、取消或 UNKNOWN 的人工接管流程。订单和支付合在最小夹具中，完整拆分场景属于 T05。HTTP 实验服务使用独立临时凭证，不应当作为生产 API 暴露。

故障注入精确覆盖“下游提交后响应不完整”和“收到响应、本地落库前退出”两个窗口；没有模拟宿主机断电、磁盘损坏、数据库灾备或外部支付系统的可用性。未验证的这些场景不属于 T04 完成声明。
