# T09：完成受控执行与结果确认

## 范围与依赖

依赖 T05 的模拟业务幂等接口、T07 的持久化认领及租约、T08 的冻结方案与审批（提交 `244b688`）。开始时工作区干净。本次完成批准后的复核、执行意图、受控修复、操作查询和最终业务验证。只处理支付成功但订单待支付这一动作；不实现 T10 的取消/人工登记接口、T11 的真实诊断或 T13 前端。

## 实现与文件

- `backend/.../execution/ExecutionClient.java`：分离读/执行凭证，固定服务 origin，HTTP 连接及请求超时，不自动重发修复；响应异常/404/不可用保守处理。复核订单与支付，解析并核对操作 ID 和所有固定参数。
- `ExecutionMapper.java`、`ExecutionTransactions.java`：APPROVED/EXECUTING/UNKNOWN/VERIFYING 认领，短事务锁任务并再次核验审批、版本、摘要、有效期。意图、操作 ID、EXECUTING 状态、复核证据、审计原子保存；租约/owner/epoch/状态/版本拦截旧写回。
- `ExecutionWorker.java`：唯一新意图的提交者发送修复；所有恢复只查询原操作 ID。确认结果持久化退避；不确定或验证查询超过 5 分钟转人工且保留 guard。成功响应还须后续业务事实验证，不能直接标成功。
- `ExecutionRecords.java`：固定参数及事实/结果校验；身份不一致、金额/币种/支付关联不一致、版本变化均不能通过。
- `ExecutionController.java`：范围内只读 `GET /api/tasks/{id}/execution`；任务增加 VIEW_EXECUTION，基础审计增加 EXECUTION_INTENT / EXECUTION_PROGRESS。证据增加 EXECUTION_PRECHECK / EXECUTION_VERIFICATION。
- `V5__controlled_execution.sql`：execution 表及索引，operation_id 主键、task_id/plan_id 唯一，数据库触发器保护执行身份与期限。旧迁移不改。
- application.yaml、Compose、`.env.example`：后端新增 SIMULATOR_EXECUTE_TOKEN 映射及 EXECUTION_HTTP_TIMEOUT_MS（默认 3000，100—5000）。执行 Worker 只有纯 demo/test、启用 Worker 且读/执行凭证齐全才认领。没有新增依赖。
- 适配 FoundationIT 迁移计数为 5，WorkerLeaseIT 临时库清理包含新增 FK 表。既有审批/创建测试不配置执行凭证，保留各自验收范围。

接口见 [受控执行](../api/execution.md)，决策见 [009](../decisions/009-t09-controlled-execution.md)。

定向测试已通过：ExecutionIT 8 项真实 PostgreSQL 测试，T09ExecutionIT 6 项独立 JVM/HTTP 集成测试。新增 ExecutionPolicyTest 3 项业务边界单元测试。

| 验收要求 | 对应证据 |
| --- | --- |
| 正常闭环完成 | 两个真实 Worker 竞争；一个意图、一个下游操作、订单版本 1→2，最终验证证据落库后 FINISHED/REPAIR_VERIFIED |
| 订单变化会被拦截 | 审批前后订单已关闭或版本变化时转 MANUAL，不生成意图、不调用业务写接口；支付关联/币种/金额亦有校验测试 |
| 响应丢失进入 UNKNOWN | 模拟服务提交后延迟 2 秒，调用方请求超时 500ms；持久化 UNKNOWN 步骤，随后查询原 ID 并验证成功 |
| 未查到不盲目重试 | 专用数据库构造已提交未发送意图，真实 HTTP 返回 404；多次查询后仍 UNKNOWN，下游操作数保持 0，guard 保留 |
| 成功必须有业务证据 | 下游成功仅进入 VERIFYING；重新查询匹配才成功，验证不匹配转 MANUAL 并保留限制 |
| 执行意图与审批约束 | 无审批、拒绝、过期不能开始；竞争认领/重复开始只产生一个意图；审计失败整体回滚 |
| 进程恢复和旧 Worker | 旧租约不能创建意图或覆盖新结果；真实 SIGKILL 调用方后由新 JVM 查询原 ID，最终下游效果一次 |

进程退出实验的边界：测试数据库临时约束阻止执行结果/步骤写回，在确认下游已提交后杀死调用方容器（KILL）；解除测试约束并将该测试任务租约设为已过期，再启动新 JVM。它验证真实进程退出和持久化恢复，但没有等待生产默认 30 秒租约自然到期。未查到案例是显式构造恢复位置，不冒充真实进程退出。

## 限制与后续

业务执行、数据库事务、HTTP、并发与进程恢复均实际运行；业务数据仍是隔离模拟订单，不涉及真实资金。诊断方案仍为 TEST_STUB，没有真实模型调用或模型质量评测。

首次意图提交后若请求尚未发出就退出，恢复不自动重发，可能超时转人工；这是第一版对“未查到”的保守策略。T10 补取消与人工处置入口，不能直接清掉未知任务的订单限制。T11 才接实际诊断。

没有新增前端交互，没有对既有演示数据库执行迁移或部署服务，没有自动推送。升级部署后，配置齐全的执行 Worker 会接续尚未过期的既有 APPROVED 任务；运行前应了解这一行为。
