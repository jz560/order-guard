# T05：业务模拟服务与场景重置边界

## 问题与约束

T04 的 `t04_probe` 是独立协议实验，其订单和支付保存在最小夹具中。T05 需要常驻 HTTP 服务、分开的业务证据、六个可重现场景和受控修复，同时不能损坏原实验或破坏操作 ID 幂等。

## 选择

- 新增默认 Flyway V2，建立 `orders`、`payments`、`callbacks`、`operations` 和 `simulation_scenarios`；保留 T04 的 schema、迁移和进程入口。
- 修复先通过操作主键预留并锁定记录，逐字段比较固定参数；同 ID 不同参数返回 409。新操作按场景、订单、支付顺序加锁，在同一 PostgreSQL 事务中校验事实、更新订单并保存结果。明确业务拒绝也持久化，重放返回原结果。
- 操作记录直接保存并比较全部固定参数，不依赖 JSON 序列化顺序或仅比较哈希。单一动作使用枚举，金额使用整数分，第一版仅 CNY。
- 场景重置锁定场景记录，创建带 UUID 的新订单与支付 ID，切换活动订单指针，清除该场景故障。旧订单、证据和操作保留可查询；旧操作重放仍返回原结果，针对旧订单的新操作拒绝。重置不冒充业务撤销，后续上游任务必须重新取得活动订单 ID。
- demo/test 首次启动幂等初始化六个场景，后续启动不覆盖已有状态。管理接口要求独立 ADMIN Bearer 凭证；只有全部生效 profile 都属于 demo/test 才允许管理和故障执行，混合 production/demo 也关闭。普通读凭证不能写，执行凭证不能重置，ADMIN 不具有业务执行权限。
- 凭证缺省为空，业务入口拒绝访问；不硬编码可用凭证，不改变默认无模型密钥启动能力。Compose 示例凭证仅为本地演示。业务后端将来仅通过 HTTP 使用模拟服务。
- 延迟故障在事务提交后延迟响应 2 秒且只触发一次，可用客户端短超时复现“客户端未收到结果但业务成功”。结果查询不可用故障返回 503，直到显式清除。非 demo/test 忽略已持久化故障。

## 未采用方案

- 删除旧场景数据和操作：会丢失审计信息，并使相同操作 ID 在重置后产生第二次效果。
- 重置订单版本为 1 并复用原 ID：旧请求可能匹配新一轮订单；增加调用方运行代号又会扩大现有写接口契约。
- 在数据库事务内睡眠模拟超时：会把通信故障变成持锁问题，因此延迟放在事务外。
- 为模拟服务实现审批平台：审批和执行授权由 T08/T09 的上游服务负责；本服务是隔离的下游业务契约，执行凭证只应交给可信执行端。

## 边界与验证

正常延迟是近期支付成功且回调待送达的证据快照，不自带定时回调 Worker；是否等待属于诊断策略。缺失证据场景保留订单支付引用但不生成支付记录，不能用外键强制补齐缺失证据。

本服务不会判断上游审批是否有效，也不接入真实支付；不能把此事务原子性直接用于独立真实支付系统。重置保留历史会增加数据量，T05 不提供历史删除接口。实际运行结果见 [T05](../tasks/T05.md)。
