# 009：执行意图、只查询恢复和业务结果验证

## 问题与约束

HTTP 成功、失败、超时都不能替代业务结果证明。进程可在意图提交、请求发出、下游提交、本地保存结果之间任意退出；不能靠换操作 ID 或重新创建任务规避不确定性。审批与执行之间业务事实也可能发生变化。

## 实现选择

- 单独的 ExecutionWorker 处理 APPROVED、EXECUTING、UNKNOWN、VERIFYING，复用 T07 Claim、租约、epoch、版本条件更新及步骤记录。诊断 Worker 保留原状态范围。使用同一 Spring 调度基础设施，不增加队列或外部平台。
- 执行前 HTTP 查询在事务外。随后锁任务，在短事务内重查方案/批准/有效期和认领条件，创建 execution 并转为 EXECUTING。execution 对 task_id、plan_id 分别唯一；operation_id 为主键，身份、摘要、起止时间用数据库触发器保护。动作/参数继续引用不可变 plan。
- EXECUTING 转换是授权开始边界。已开始的操作之后只确认，不因审批过期而丢弃查询；尚未开始的过期审批不能产生意图。即使陈旧 Worker 恢复发出已获授权的请求，下游仍绑定同一 ID/参数，且未知订单限制一直保留。租约只保护本地写回，不能取消已发出的网络请求。
- 新意图提交者才走首次发送路径；所有接管/重启从 EXECUTING 或 UNKNOWN 恢复时只查原 ID。404 不解释为未执行，不自动重发。保守代价是“意图已提交、尚未发送就退出”可能最终转人工；这是技术设计指定的第一版策略。
- 读与执行凭证分离；固定 origin、禁用重定向、连接/请求超时、限制响应大小，反序列化失败保守视为不确定。响应须绑定 operationId、全部固定参数；成功还须合法 before/afterVersion。这里只保证业务效果幂等，不承诺网络包恰好发送一次。
- 下游成功先 VERIFYING，重新读取订单及支付，确认 PAID、版本与事实，再同事务保存验证证据、成功状态、审计并释放 guard。业务事实不匹配或持续不可确认保留 guard。下游明确拒绝才以拒绝结果结束并释放 guard。
- 查询退避和 5 分钟确认期限持久化，进程重启不重置期限。到期转人工仍保留订单限制，不把结果未知写成失败。取消/人工结果登记接口仍由 T10 实现。

## 验证与适用边界

测试包括真实 PostgreSQL 的竞争认领、旧租约/epoch 拦截、原子意图回滚、过期/无批准拦截、最终事实验证，以及独立服务 HTTP 的正常闭环、响应丢失、未查到不重发和调用方 SIGKILL 恢复。完整结果见 [T09 交付记录](../tasks/T09.md)。

业务数据仍为模拟服务。订单和支付由下游在同一事务内核验；不能直接套用于真实外部支付系统。方案仍由固定测试替身生成；真实 Agent 诊断属于 T11。未实现自动重发和通用重试引擎，避免把“没查到”误认为安全重发证明。
