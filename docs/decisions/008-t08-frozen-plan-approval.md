# 008：冻结方案和唯一审批决定

## 约束

审批必须绑定固定订单、动作、参数、方案版本和有效期。并发批准、拒绝或响应丢失后的重试不能形成多个决定。T08 仍使用测试诊断，不提前实现 T09 的执行意图和下游写请求。

## 选择

- Worker 在租约/epoch/版本条件更新成功后，同事务插入冻结方案、步骤和审计。任何写入失败整体回滚；旧 Worker 无法留下方案。方案引用持久化订单证据，source 明确为 TEST_STUB。
- 参数采用固定字段顺序、受限 ASCII 标识符、整数金额和 CNY 的 JSON，摘要包含动作。数据库保存原始规范文本，避免 jsonb 重排影响摘要。
- plan 的 `(task_id, version)` 唯一；approval 的 plan_id 唯一。冻结方案和最终决定均用触发器拒绝 UPDATE/DELETE，不提供修改或删除 API。
- 审批事务先锁任务，再检查最新方案、版本、摘要、角色、有效期、任务状态，原子写状态、审批、审计。角色与订单范围在服务端检查，actor 来自认证上下文。
- 相同最终决定重放不更新任何状态；不同决定、原因或审批人发生冲突。过期后的重放只是读取历史，不延长授权。
- 使用数据库时钟和状态更新中的到期条件，避免等待行锁期间过期仍可批准。后台对 WAITING_APPROVAL/APPROVED 的最新过期方案采用 SKIP LOCKED 扫描，结束未开始执行的任务并释放订单限制；EXECUTING/UNKNOWN 等状态不参与过期收尾。
- 15 分钟有效期固定来自设计默认值，无额外配置平台。批准保留订单限制，明确拒绝与执行前过期释放限制。

## 未采用及边界

不使用“客户端禁用按钮”作为授权，不覆盖旧审批，不用内存去重，不在审批事务内调用 HTTP。当前没有方案编辑/重生成接口；将来变更参数须新增方案 ID/版本，并在相同任务锁下撤销旧版本的可执行资格，重新审批。

当前 APPROVED 不可被 Worker 认领执行，因此重复审批没有业务效果。T09 必须在执行意图事务内重新检查批准、最新方案、参数摘要、到期时间和当前业务事实，给 execution.plan_id 加唯一约束；不能仅凭 task.state=APPROVED 执行。

V4 升级保留 T07 步骤历史，将旧无方案等待任务恢复诊断。测试方案不证明支付成功或修复合理性；T11 才接入真实诊断。

验证结果及证据见 [T08 交付记录](../tasks/T08.md)。
