# 004：先用隔离实验验证写操作协议

## 问题与约束

T04 要证明真实 Java 调用方在丢失 HTTP 响应、收到结果但未本地落库便被 SIGKILL 时，能够从 PostgreSQL 中恢复。HTTP 失败不能等同于业务失败，恢复不能依赖调用方内存，也不能访问下游数据库。

T05 尚未建立完整业务模拟，T06/T08 尚未建立正式任务与审批；不能为实验开放普通服务的写接口或绕过未来审批。

## 选择

在现有两个模块内加入显式启动的 demo/test CLI：`T04Caller` 和 `T04Downstream`。它们不注册为 Spring Bean；Mapper 也仅由实验自行注册。独立 Flyway location 在各自数据库的 `t04_probe` schema 建表。默认服务的 `db/migration` 保持原状。

调用方按操作 ID 保存不可变参数，先提交 PREPARED，再原子认领为 IN_FLIGHT，之后才发送 HTTP。数据库事务不跨越 HTTP 等待。该最小实验始终保留订单唯一限制，终态也不释放；正式限制释放留给 T06/T10。

下游先以操作 ID 插入保留记录，锁定该记录，比较规范化参数的 SHA-256 和完整参数。相同 ID 不同参数返回 409。然后锁订单，核验支付成功、关联、金额、币种、订单状态与版本，在同一事务内更新订单并保存结果。并发相同 ID 返回原结果；不同 ID 的订单竞争由行锁和条件更新阻止重复推进。

恢复仅 GET 原操作及当前订单：404、通信异常、非终态或绑定不一致均保留 UNKNOWN。只有可信操作结果与业务核验同时通过才保存 SUCCEEDED。恢复进程不持有写凭证。没有自动重试、后台恢复扫描、租约或取消语义；这些属于后续任务。

## 放弃的替代方案

- 内存保存 operationId：无法跨进程恢复。
- 写操作和结果记录分别提交：会产生业务已成功但无法查回结果的窗口。
- 超时后新建 ID 或直接重发：会绕过原操作的结果确认。
- H2、模拟异常代替 SIGKILL：无法证明 PostgreSQL 并发、事务与真实进程退出的行为。
- 提前实现任务/审批/Worker：超出 T04，并使协议实验与业务流程耦合。

## 边界与验证

保证的是本实验下游契约内的幂等业务效果，不承诺网络请求恰好发送一次，不代表任意外部支付系统都具备同等契约。订单与支付事实是固定模拟数据，金额 10000 分、CNY、初始版本 1。实验以 `effect_count` 辅助观察一次业务推进，它不是生产财务审计。

验证使用独立 Linux Java 容器、真实 PostgreSQL 17.6、HTTP、Docker SIGKILL 和新调用进程。实测状态及证据见 [T04](../tasks/T04.md)。没有真实模型调用或资金操作。
